# Надёжное применение конфигурации wsconfig

Дата: 2026-10-02

## Цель и границы

Пользователь поручил выполнить рекомендации архитектурного анализа:
внешний backup с проверкой восстановления, журнал и блокировка применения,
очистка системных объектов по manifest, согласованная фиксация изменений в Git,
тесты критичной управляющей логики.

Сохраняем Ubuntu, Nix/home-manager и существующих владельцев слоёв.
Не меняем аппаратные параметры, режим сна, загрузки и настройки рабочего
desktop. Новые механизмы сначала проверяются на временных каталогах;
исполняемые bin/ связаны с checkout, поэтому изменение этих файлов сразу
меняет команды установленной системы.

Работа разделена на три последовательных блока. Эта спецификация подробно
определяет первый; следующие требуют собственных решений перед реализацией.

## 1. Журнал, блокировка и жизненный цикл manifest

### Подход

Добавить небольшой общий модуль операций и отдельный модуль обработки
manifest. bin/ws остаётся маршрутизатором и координатором существующих
действий. Не вводить отдельный daemon, базу данных или новый менеджер
конфигурации. Bash подходит для orchestration, Python стандартной библиотеки
— для проверки manifest, файлов и структурированного журнала.

Варианты полного транзакционного rollback и полной переписи ws отклонены:
они значительно расширяют область работы; рестарты служб, initramfs и
операции владельцев всё равно нельзя надёжно откатить одной файловой
транзакцией. Предлагаемый механизм явно записывает частичные результаты.

### Блокировка

- Одна блокировка workstation на пользователя и хост сериализует
  `ws switch`, `ws system apply`, `ws apply`, `ws update`.
- Блокировка берётся до первой мутации, с помощью flock, без ожидания.
  Конкурирующая команда завершается с понятным сообщением, не выполняя
  изменений. Дескриптор освобождается автоматически при выходе процесса.
- Вложенные операции (`ws update nix` вызывает switch) выполняются в рамках
  уже взятой блокировки. Вложенность определяется явным внутренним вызовом,
  а не произвольной переменной окружения, разрешающей обход блокировки.
- Прямой запуск wsflatpak/wsbox остаётся возможен; общий lock гарантирует
  сериализацию входных команд ws, а не всех произвольных внешних действий.
- `ws check`, `ws diff`, чтение manifest и просмотр журнала lock не берут.

### Журнал

- Журнал хранится в `~/.local/state/workstation/operations/`, по отдельному
  каталогу на запуск. Каталог имеет права 0700, файлы — 0600.
- Метаданные: версия формата, уникальный ID, хост, операция, время начала,
  commit, наличие локальных изменений, исходное поколение home-manager и
  последнее успешное системное дерево, целевое дерево после его сборки.
- События имеют формат JSON Lines: время, этап, начало/успех/отказ,
  exit code, безопасное краткое описание действия.
- Не записывать всё окружение, секреты, содержимое файлов или неограниченный
  вывод дочерних процессов. Их привычный вывод остаётся в терминале.
- Итог сохраняется при штатном завершении, ранней ошибке, SIGINT и SIGTERM.
  SIGKILL/потеря питания оставляют запуск без итогового события; просмотр
  журнала обозначает его как незавершённый, без утверждения причины.
- Указатель `system/applied` означает последнее успешно применённое дерево.
  Отказ не должен заменять его. Целевое неуспешное дерево сохраняется
  отдельным GC root операции для диагностики и повторного применения.
- Старый `system/history` сохраняется совместимым; новые подробные данные
  хранятся отдельно. `ws operations list` и `ws operations show ID`
  показывают результат и последнюю выполненную фазу.
- Повторный apply обычным способом исправляет частичное состояние. Отдельный
  автоматический resume/rollback в первой версии отсутствует.

### Проверка manifest до изменений

- Сохранить действующий TSV-контракт: file, esp, unit, restart, watch.
- Проверить число полей, допустимые виды записей, режимы доступа, абсолютные
  file/watch пути, отсутствие управляющих символов и компонентов `..`.
- Дубликаты file/esp путей и конфликтующие состояния unit отклоняются.
- Ошибочный manifest отклоняется до sudo и любых изменений целевых файлов.
- Проверка уже существующей системы сохраняет JSON-контракт lib/check.bash.

### Удаление файлов, исчезнувших из декларации

- Источник предыдущего состояния — последнее успешное применённое дерево.
  Отсутствие такого дерева означает отсутствие автоматической очистки;
  старые известные миграции остаются отдельным совместимым механизмом.
- Сравниваются только записи `file`. `esp` и `watch` не означают владение
  установленным файлом и никогда не используются для удаления.
- Кандидат — путь, который принадлежал предыдущему дереву, но исчез из нового.
- Автоматическое удаление допустимо только для обычного файла, чьи содержимое,
  режим и владелец совпадают с предыдущей декларацией. Перед удалением он
  копируется в существующий каталог backup текущей операции.
- Symlink, файл через подменённый symlink в родительском пути, директория,
  несовпадающие содержимое/права/владелец сохраняются. Рекурсивное удаление
  отсутствует. При изменении файла после проверки он также сохраняется.
- Отсутствующий кандидат считается уже удалённым.
- Сохранённый изменённый кандидат записывается в отдельный список unresolved
  объектов с исходным деревом. Следующий успешный apply не должен забыть его.
  `ws system check` продолжает предупреждать о нём, пока файл существует.
- Изменения modprobe/grub и других файлов при удалении должны запускать те
  же завершающие действия, что и установка соответствующего файла.
- Units, исчезнувшие из manifest, выводятся как требующие отдельного решения.
  Автоматическое выключение неизвестной работающей службы не добавляется.
- `ws system diff` показывает кандидатов и причины сохранения до apply.
- Установка новых файлов сохраняет существующий backup и проверку результата.
  Замена отдельного обычного файла должна использовать временный файл рядом
  с целевым и rename; весь apply при этом не объявляется атомарным.

### Тестирование и интеграция

- Тесты выполняются стандартными средствами Bash/Python и не требуют sudo,
  реальной смены поколения, запуска VM, перезапуска GNOME или правки /etc.
- Модули принимают явные пути входного дерева, предыдущего дерева, корня
  файловой системы и state directory. Это рабочие интерфейсы, а не скрытые
  переключатели безопасности в публичной команде ws.
- Команды с системными побочными эффектами заменяются тестовыми executables
  только на границе интеграционного теста; проверяется реальная файловая
  логика и реальный lock.
- Сценарии: параллельный запуск; вложенная операция; отказ после первого
  действия; освобождение lock после ошибки/сигнала; незавершённый журнал;
  повторный apply; корректное удаление; сохранение изменённого файла,
  symlink и директории; сохранение unresolved после следующих apply;
  первый запуск без предыдущего дерева; некорректный и дублирующий manifest;
  отсутствие обновления applied при отказе.
- Тесты интегрируются в один документированный запуск. flake checks
  продолжают собирать существующие host outputs; pure-тесты добавляются в
  checks, если не потребуют новых зависимостей или аппаратного окружения.
- Перед завершением: полный набор новых тестов, сборка flake checks обоих
  хостов, ws check repo, git diff --check. Полный ws check используется
  отдельно как проверка живого состояния, с учётом запуска контейнеров.
- Запуск нового system apply на живом хосте — после успешных тестов и
  предусмотренного документацией snapshot. Кандидаты удаления заранее
  просматриваются; аппаратные изменения не входят в эту работу.

## 2. Согласованная фиксация изменений в Git

Следующий блок: отделить применение от коммитов. Предпочтительный вариант —
ws switch собирает и применяет конфигурацию, но сам не коммитит списки.
Новые источники должны быть известны Git для flake; проверка перед сборкой
должна охватывать не только *.nix и flake.lock, но и новые используемые assets.

История создаётся одним явно проверенным коммитом связанных файлов;
существующий staged пользовательский материал нельзя включать случайно.
Нужны тесты отказа сборки, отсутствия неявного коммита, сохранения index и
обработки новых source assets. Обновляются usage, README и runbooks.
Изменение этого пользовательского интерфейса оформляется отдельной
спецификацией после первого блока.

## 3. Внешнее резервное копирование

На момент обследования виден только внутренний SSD. Пользователь выбрал
удалённый Unraid-сервер с Btrfs-разделом. SSH-адрес, пользователь, целевой
путь, желаемая периодичность и политика хранения пока не определены.
Запрошены параметры доступа; используются существующие SSH-настройки,
секреты не записываются в репозиторий.

Перед выбором транспорта проверить реальный целевой filesystem и поддержку
subvolumes по указанному пути: название share само по себе не доказывает,
что операции выполняются непосредственно на Btrfs. Выбор btrfs send/receive
или файловой передачи со snapshots принимается в backup-спецификации после
проверки доступа, прав и состава копируемых данных.

Первый deliverable этого блока — спецификация после ответа пользователя:
явные включения HOME, исключения восстанавливаемых cache, полный набор
состояния VM (диски, NVRAM, TPM, XML), проверка доступности внешней цели,
согласованности VM и восстановление в отдельный каталог.

Нельзя объявлять backup готовым по наличию скрипта или локальной копии на
том же SSD. Критерий завершения — запись на выбранную внешнюю цель и
успешный restore test HOME и выбранной VM, если VM имеются. При отложенном
носителе механизм и тесты можно подготовить, но фактический backup и restore
остаются явно незавершёнными. Расписание не включается до определения цели
и политики хранения.

## Порядок исполнения

1. Согласовать эту письменную спецификацию.
2. Подготовить подробный план первого блока и согласовать способ исполнения.
3. Реализовать первый блок через тесты на временной файловой системе.
4. Проверить сборки и документацию, выполнить review и интеграцию.
5. Выполнить блок фиксации Git отдельным небольшим изменением.
6. Выполнить backup-блок после выбора места хранения.

Предпочтительный способ исполнения — последовательно в текущем чате.
Изолированный worktree предпочтителен из-за активных ссылок в checkout;
его создание требует выбора пользователя по правилам навыка worktrees.
Текущие изменения ChatGPT launcher и remote сохраняются отдельно от новых
изменений и не включаются автоматически в коммиты этой работы.
