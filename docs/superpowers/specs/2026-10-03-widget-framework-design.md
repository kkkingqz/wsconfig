# Переиспользуемый framework виджетов Quickshell

Дата: 2026-10-03. Статус: реализация в ветке wsconfig; автоматические и runtime
проверки выполнены, live проверка GNOME-кнопок ожидает нового входа в сессию.

## Задача и критерий результата

Создать основу для нескольких собственных виджетов в текущем Ubuntu GNOME:
каждый виджет имеет кнопку верхней панели и окно заданного логического размера,
которое анимированно раскрывается под кнопкой и правильно отображается при
системном масштабе. Новый виджет добавляется компонентом QML и записью в реестре,
без изменений GNOME-расширения, IPC и общего управления окнами.

UI, состояние и анимации остаются независимыми от desktop environment.
Позже адаптер Hyprland сможет использовать эти же компоненты. Реализация
Hyprland и содержательных системных виджетов не входит в первый этап.

Основание: запрос пользователя и рассмотренный документ
`/home/king/Downloads/quickshell-widget-architecture.md`. Документ является
архитектурным ориентиром, а этот проект уточняет оконную интеграцию GNOME.

Подтверждённая среда: GNOME Shell 50.1, Wayland, экран eDP-1 3072×1920,
scale 1.5, логическая область 2048×1280; Qt/Qt Wayland 6.10.2 установлены
через apt. `qs` и `quickshell` в PATH не найдены. Репозиторий — `~/wsconfig`.
Scoped Quickshell 0.3.0 / Qt 6.11.2 проверен на этой машине при DPR 1.5.
Результаты и незавершённая live матрица: `tests/widgets/live-checklist.md`.

## Выбранный подход

Один процесс Quickshell, один реестр виджетов и одно расширение GNOME для
всего реестра. Каждый виджет — обычный QML Item с собственным содержимым.
Поверхность, состояние раскрытия, анимация и связь с desktop adapter общие.

Альтернативы: отдельный процесс и extension для каждого виджета упрощают
изоляцию отказов, но дублируют запуск, IPC и оконную интеграцию. Полностью
нативные GNOME popup дают стандартное поведение меню, но требуют переписывать
UI при переносе. Общий runtime выбран ради повторного использования и переноса.

GNOME adapter отвечает за размещение и фокус окна, поскольку FloatingWindow —
обычное Wayland toplevel. Передача x/y клиенту через IPC сама по себе не даёт
права размещать такое окно. Extension использует Meta.Window со стороны Shell.
Это расширяет адаптер относительно исходного документа, сохраняя общий UI.

## Структура в существующем репозитории

```text
widgets/
  widgets.nix                  Home Manager: config, manifest, service
  registry.nix                 единственный реестр включённых виджетов
  runtime/                     локальная доставка совместимого Quickshell
  quickshell/
    shell.qml                  композиция runtime и выбранного адаптера
    framework/
      qmldir
      WidgetRegistry.qml       загрузка и валидация manifest
      WidgetController.qml     единственный владелец состояния видимости
      WidgetHost.qml           загрузка содержимого по записи реестра
      WidgetIpc.qml            публичные команды и сигналы
      PopupFrame.qml           общий фон, отступы, обрезка и анимация
    adapters/
      gnome/
        GnomePopupWindow.qml   FloatingWindow и handshake с extension
    widgets/
      example/Widget.qml       демонстрационный виджет 420×580
      compact/Widget.qml       второй виджет 320×240
gnome/extensions/workstation-widgets@local/
  metadata.json
  extension.js                 enable/disable и сборка адаптера
  lib/
    panelButtons.js            кнопки, действия, индикация
    ipcClient.js               асинхронные вызовы и подписка
    windowPlacement.js         поиск окон, положение, фокус
bin/ws-widgets                 start/stop/restart/status/check и IPC CLI
tests/                         проверки состояния и интеграционных контрактов
docs/runbooks/widgets.md       добавление виджета, запуск, проверка, откат
```

Названия файлов задают границы ответственности. Создаются только нужные
модули; каталоги сервисов, тем и адаптер Hyprland появятся при реальной потребности.
Framework пока живёт внутри wsconfig. Извлечение в отдельный пакет возможно
после появления нескольких рабочих виджетов, публикация пакета не требуется.

## Реестр и контракт виджета

`registry.nix` хранит записи: `id`, `enabled`, `label`, `iconName`,
`component`, `width`, `height`, `panelPosition`, `panelOrder`.
Размеры — положительные целые логические пиксели; ID соответствует
`[a-z][a-z0-9-]*`, уникален; component — относительный путь внутри
доставляемого QML-каталога. panelPosition принимает left/center/right.
По умолчанию right; order задаёт порядок кнопок внутри группы framework.

Nix генерирует один JSON manifest с `schemaVersion: 1`. QML и GNOME читают
один файл; отдельных списков кнопок в extension нет. Невалидный manifest
не запускает виджеты и выдаёт понятную ошибку; несовместимая версия схемы
отклоняется. Пути и существование компонентов проверяются при сборке.

Компонент виджета — Item, получающий `context` с ID, текущим размером
содержимого, фазой раскрытия и методом запроса закрытия. Он не создаёт окно,
не запускает qs и не импортирует desktop-specific API. Framework размещает
его внутри PopupFrame. Декоративные отступы и область тени учитываются отдельно
от указанного в реестре размера панели; эти значения общие и документированы.

В первом этапе два demo используют один framework. example показывает
нейтральное содержимое, кнопку закрытия и диагностические размеры/DPR;
compact — другое содержимое и размер. Это проверяет отсутствие привязки
framework к одному ID, размеру или QML-компоненту.

## Runtime и состояние

Один процесс, одно окно на запись реестра, содержимое загружается при первом
открытии и сохраняется до остановки runtime. В каждый момент раскрывается
один виджет: переключение кнопок закрывает предыдущий и открывает выбранный.
Controller владеет target visibility; extension получает состояние и не
держит независимый флаг open. При рестарте все виджеты закрыты.

Фазы: `closed → preparing → opening → open → closing → closed`.
Preparing включает создание поверхности и позиционирование. Повторный
toggle во время opening/closing меняет целевую видимость, анимация продолжает
движение от текущего progress. Во время preparing закрытие отменяет раскрытие.
Каждая попытка открытия получает requestId; устаревший placement ack игнорируется.
Переключение на другой виджет начинается после завершения закрытия предыдущего.

PopupFrame анимирует progress 0..1 примерно за 180 мс: раскрытие сверху
вниз через clipping и прозрачность. Размер Wayland-окна во время анимации
не меняется. Обратная анимация завершается до visible=false. Анимации можно
отключить общей настройкой, учитывается GNOME enable-animations.

Окно прозрачное с первого создания, без обычных декораций. Возможность
отключить Qt Wayland decorations и взаимодействие с GNOME map-анимацией
проверяются на раннем прототипе. Любая необходимая настройка Qt задаётся
только процессу виджетов. Анимация содержимого остаётся в QML; возможное
подавление стандартного оконного эффекта относится к GNOME adapter.

## IPC и синхронизация

Внешний target `widgets`, общий для всех виджетов:

```text
toggle(id: string): bool
show(id: string): bool
hide(id: string): bool
hideAll(): void
status(): string              JSON snapshot с protocolVersion: 1
```

Snapshot содержит runtime instanceId, выбранный widgetId, target visibility,
фазы, requestId, revision и последнюю ошибку. Команды возвращают true, если
запрос принят, и false для неизвестного/недоступного ID; это не обещание
завершения анимации. Один сигнал `stateChanged(snapshot: string)` передаёт полный
snapshot; он позволяет extension восстановиться без воспроизведения истории.
Неизвестный ID возвращается диагностикой и не меняет другие окна.

Внутренний GNOME handshake отделён от публичных команд: `adapterReady`,
`renewAdapterLease(instanceId)`,
`placed(id, requestId)` и `placementFailed(id, requestId, reason)`.
Controller сначала запрашивает подготовку поверхности, extension обнаруживает
её, размещает и активирует окно, затем подтверждает placement. Только после
ack QML раскрывает содержимое. Таймаут подготовки — 2 секунды; при отказе
окно скрывается, состояние возвращается в closed и сообщается причина.

Выбранный Quickshell должен поддерживать IPC signals/listen (документация
0.3.1). Extension использует Gio.Subprocess асинхронно, аргументы массивом,
конечные таймауты вызовов, одну долгоживущую подписку и ограниченный reconnect.
Команды и snapshot обрабатываются последовательно. Подписка начинается до
запроса status; порядок обновлений определяется instanceId и номером revision.
Систематический polling и отдельный D-Bus backend не нужны.

Команды всегда адресуют именованную конфигурацию `workstation-widgets`:
`qs -c workstation-widgets ipc call widgets toggle example`.
Extension получает абсолютный путь qs из генерируемой runtime-конфигурации,
не зависит от PATH GNOME Shell и не запускает отдельный runtime при каждом клике.

## GNOME-адаптер

Extension создаёт кнопки через PanelMenu.Button/St.Icon и addToStatusArea.
Кнопка клавиатурно доступна, имеет label и показывает выбранное состояние
по snapshot runtime. Shell API изолирован в этом extension, target GNOME 50.

Окно сопоставляется с ID по фиксированному title namespace
`workstation-widgets:<id>` и PID активного runtime. PID и instanceId приходят
из status; одного заголовка для управления чужим окном недостаточно.
Сопоставление делается заново при пересоздании поверхности или рестарте.

Положение вычисляется из реальной геометрии кнопки, панели, рабочего участка
монитора и frame rect окна: под кнопкой с зазором 8 логических пикселей,
по центру кнопки, с ограничением по краям рабочей области. Desktop координаты
GNOME и Qt не перемножаются вслепую: преобразование и размеры frame/content
проверяются по actual geometry и API выбранной версии Mutter.

Если заданная панель не помещается, host ограничивает доступный размер
рабочей областью минус отступы и даёт прокрутку содержимого. Qt сохраняет
системный масштаб, framework не уменьшает весь UI дополнительным scale.
При смене мониторов/scale открытая панель пересчитывает положение и лимиты.

Повторная кнопка и Esc закрывают окно. Потеря фокуса на другое окно закрывает
панель после проверки новых событий, чтобы клик по собственной кнопке не
вызывал hide+toggle с повторным открытием. Потеря фокуса сама по себе не
эквивалентна любому клику снаружи: pointer events GNOME должны покрывать
клик по фону и другим элементам Shell, не перехватывая доставку клика.
Контекстные меню/дочерние поверхности относятся к виджету и не закрывают его.

При переходе в overview, блокировке и смене workspace окно скрывается.
При disable extension закрывает соединение и удаляет свои кнопки,
сигналы, таймеры и асинхронные операции. Постоянный Unix-сокет заменяет lease и CLI IPC. Обрыв adapter немедленно
закрывает GNOME-поверхности. Протокол и конфигурация версии 2 определены в
`2026-10-04-widget-socket-design.md`; этот документ задаёт актуальный транспорт.


Поведение в Alt-Tab, Ubuntu Dock, поверх обычных окон и с Tiling Assistant
проверяется отдельно. Для window lists используется доступный Meta API;
его фактическое действие на GNOME 50 фиксируется в runbook. Не обещается
эквивалентность нативному GNOME popup до этих проверок.

## Масштабирование

Все размеры QML, отступы и progress-анимации используют логические координаты.
Qt Wayland выполняет масштабирование. Панель 420×580 при scale 1.5 занимает
630×870 физических пикселей без учёта декоративной области. Не выставляются
глобальные QT_SCALE_FACTOR/QT_SCREEN_SCALE_FACTORS и не читается global
gsettings scaling-factor как масштаб всех мониторов.

Используется DPR конкретного окна для диагностики и растровых ресурсов;
текст и векторные ресурсы отрисовываются Qt. При дробном масштабе округление
не должно обрезать края и тень. Изменение text-scaling — отдельная настройка:
макет допускает более крупный текст и прокрутку, а соответствие GNOME font
settings проверяется отдельно от monitor scale.

## Доставка и интеграция wsconfig

`widgets/widgets.nix` импортируется из nix/home/default.nix. Registry JSON,
runtime config и service доставляет Home Manager. Исходники QML связаны с
checkout по существующему паттерну mkOutOfStoreSymlink. Настройки и список
виджетов изменяются через Nix и ws switch.

Quickshell доставляется как отдельный Nix runtime closure, привязанный к
lock и доступный только launcher/service. Если основной nixpkgs не содержит
нужную версию, widgets/runtime использует независимый flake с совместимым
release. Не заменяются host Qt/GTK, GNOME, portals, session variables или
graphics stack. Ранний технический этап проверяет загрузку Qt Wayland,
рендеринг через host GPU/Mesa и поддержку IPC выбранной сборкой.

User service связан с graphical-session.target и GNOME-сессией, запускается
один раз, останавливается с сессией, использует on-failure с ограничением
рестартов. WAYLAND_DISPLAY и session D-Bus берутся из окружения действующей
сессии. Будущий Hyprland adapter использует свой launcher без второго
процесса этой же конфигурации.

UUID добавляется в существующий gnome/gnome-extensions.nix. Установщик
ws-keyboard-install-extensions расширяется для локальных JS-модулей и assets:
доставляет всё необходимое дерево extension, проверяет файлы и удаляет только
устаревшие принадлежащие этой поставке файлы. Текущее поведение других
расширений и компиляция schemas сохраняются. Проверки ws-gnome учитывают
многомодульное расширение. Новый Shell extension может потребовать нового
входа в Wayland-сессию; процесс не перезапускает Shell и не завершает сессию.

`ws-widgets` управляет только собственным service, выводит status и checks.
Команда check read-only: runtime/manifest, service, IPC, активность extension,
согласованность runtime instance и готовность оконного адаптера. Связь с
общим ws check добавляется по существующему формату lib/check.bash.

## Проверки и границы первого этапа

Автоматически проверяются ошибки реестра, адресация разных ID, snapshot
revision/instance, повторные toggle, отмена preparing, устаревший ack,
переключение виджетов и закрытие после завершения анимации. Проверки
установщика подтверждают доставку lib/ и удаление устаревшего owner-файла,
сохранение сторонних файлов и существующую обработку schemas.

В GNOME проверяются оба demo, текущие 150%, допустимые дополнительные
масштабы и доступный внешний монитор с другим scale, если подключён;
отсутствие рамки, вспышки, двойной анимации и перехвата невидимыми областями;
Esc, внешний клик, быстрые переключения, overview, workspace, lock/unlock;
остановка/рестарт runtime и disable/re-enable extension. Отсутствие внешнего
монитора записывается как непроверенный сценарий, а не успешный результат.

Готовность framework означает, что compact добавляется только новым QML
компонентом и записью реестра, обе панели корректно работают при 150%, а
адаптер не содержит знания об их содержимом. Не входят: магазин плагинов,
hot installation, произвольные сторонние компоненты, backend системных
сервисов, настройки тем и реализация Hyprland.

## Риски и порядок разрешения

Сначала проверяется совместимый runtime и минимальное прозрачное окно:
декорации, actual size/DPR, обнаружение Meta.Window, placement handshake,
фокус и GNOME map effect. Если эта связка не даёт нужного поведения, причина
фиксируется и пересматривается только window adapter, до разработки UI.
Работа с API GNOME 50 изолируется и требует повторной проверки после обновлений.

Потеря runtime сбрасывает кнопки и закрывает зарегистрированные поверхности;
ошибка отдельного QML-компонента помечает соответствующий виджет недоступным
и не запускает бесконечный цикл открытия. Процесс общих компонентов остаётся
общей точкой отказа; независимые процессы не добавляются без реальной потребности.
