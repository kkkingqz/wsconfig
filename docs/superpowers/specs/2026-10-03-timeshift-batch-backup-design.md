# Передача всех снимков Timeshift на Unraid

## Требование пользователя

`ws backup` передаёт все существующие снимки Timeshift на сервер. После
успешного завершения удаляет собственные локальные read-only копии, кроме
последней. Следующий запуск использует оставшуюся копию как parent
инкрементальной передачи и после успеха оставляет уже новую последнюю копию.

Это изменение существующего backup в ветке `wsconfig-backup` после `a1db490`.
Адрес Unraid по-прежнему не задан: подготовка кода не включает deployment,
реальные передачи, удаление текущих локальных снимков или расписание.

## Выбранная схема

Без hooks Timeshift, worker и нового расписания. Один ручной запуск команды
делает inventory, последовательную передачу и затем локальную очистку.

Команда без аргументов `ws backup` запускает Timeshift batch. `plan`, `status`,
`check` сохраняются; существующий отдельный backup VM остаётся доступен явно.
VM не добавляются автоматически: Timeshift не сохраняет @vms.

Каждый завершённый Timeshift snapshot содержит @ (scope system) и, если
сохранён, @home (scope home). Для каждого имеющегося scope создаётся отдельная
read-only Btrfs копия в управляемом backup root. Исходный Timeshift snapshot
не меняет ro-флаг, не переименовывается и не удаляется.

Копии остаются раздельными: после очистки одна последняя для system и одна
для home. Единственный parent не может обслуживать обе независимые цепочки.
Если @home отсутствует в конкретном snapshot, inventory явно показывает это;
не создаёт копию текущего HOME и не утверждает, что HOME того момента сохранён.

## Inventory и идентичность

Снимки обрабатываются от старых к новым по времени Timeshift. В inventory
попадают только завершённые snapshots с корректными metadata и настоящими
Btrfs subvolumes на ожидаемом filesystem UUID. Путь выбирается только внутри
проверенного Timeshift storage, без symlink и произвольных root-источников.

Inventory фиксируется на начало запуска. Новые снимки, возникшие во время
передачи, попадут в следующий запуск. Если Timeshift удалил источник раньше
создания read-only копии, batch завершается ошибкой, сохраняя parent.
После создания копии отправка не зависит от дальнейшего retention Timeshift.

Обход всех существующих снимков обязателен, повторная передача подтверждённого
экземпляра — нет. Журнал хранит Timeshift timestamp, UUID исходного subvolume,
scope, UUID read-only копии, remote ID и identity configured target. Совпадение
только имени/даты недостаточно. Перед пропуском проверяются remote received_uuid
и read-only статус; отсутствие remote экземпляра требует повторной передачи.

Сохранённая копия фиксирует состояние writable Timeshift snapshot на момент
первого импорта. Повторный запуск не предназначен для версионирования изменений
после загрузки в этот же snapshot из GRUB; повторный импорт изменённого снимка
потребует явной отдельной операции, не скрытой замены удалённой копии.

## Передача

Для каждого scope первый новый snapshot отправляется относительно сохранённого
локального parent. Следующий snapshot в этом же batch отправляется относительно
предыдущего успешно переданного snapshot того же scope.

Parent проверяется локально и на сервере: UUID, received_uuid, ro. Если общего
parent нет, применяется полная передача с явной причиной в результате.
Несовпадение UUID либо writable parent вызывает отказ. Send protocol остаётся 1.
Receiver получает scope system в ограниченный whitelist, без произвольных путей.

После stream remote inspect подтверждает UUID/ro. Только затем snapshot
записывается как успешный и становится новым parent. Каждая успешная передача
фиксируется отдельно; ошибка в следующем snapshot не отменяет предыдущую.
После разрыва связи перед подтверждением следующий запуск сначала проверяет
remote ID и может подтвердить уже опубликованный snapshot вместо его замены.

## Локальная очистка

Очистка начинается только после успешной обработки всего inventory. Если
передача/проверка любого снимка не завершилась, в этом запуске очистки нет.
Последний подтверждённый parent сохранён, успешные шаги позволяют продолжить
при следующем запуске без повторной отправки уже подтверждённых экземпляров.

Перед удалением журнал с новыми parent сохраняется надёжно; целевые retained
snapshots ещё раз проверяются на обеих сторонах. Удаляются только зарегистрированные
ws backup read-only subvolumes внутри своего root, с совпадающими UUID,
отличные от retained ID. Нельзя удалять неизвестные каталоги, writable копии,
Timeshift snapshots, remote snapshots, live subvolumes или receiver partials.
Без `rm -rf`: только Btrfs subvolume delete конкретных проверенных копий.

Если очистка прервалась, новый parent остаётся сохранённым, лишние старые копии
не влияют на следующий incremental. Ошибка очистки видна в журнале и exit code;
следующий успешный запуск повторяет безопасную очистку. Повторный запуск без
новых снимков тоже может завершить ранее прерванную очистку.

Журналы переданных snapshots сохраняются после удаления read-only копий.
Remote retention в эту задачу не входит. Исходным retention управляет Timeshift.

## Восстановление

Удалённые копии старых снимков остаются доступными для восстановления.
Существующая проверка SHA-256 относительно локальной read-only копии работает
для retained snapshot. Для уже очищенного snapshot такой baseline отсутствует:
команда должна явно сообщить об этом, а не заявить проверку содержимого.
Получение старого snapshot в отдельный каталог и проверка UUID/ro сами по себе
не доказывают контрольные суммы всего содержимого. Реальный recovery test
Timeshift system/HOME выполняется после подключения NAS. VM boot test отдельно.

## Проверки и документация

Тесты проверяют сортировку, все существующие snapshots, пропуск подтверждённых,
полную первую и следующие incremental передачи, разные цепочки system/home,
несколько новых снимков за batch, отсутствие новых snapshots, remote потерю,
отказ посередине, прерванное подтверждение и прерванную очистку. Отдельно:
не удалить parent/Timeshift/writable/неизвестный snapshot, отказ при неверном
filesystem/UUID, отсутствие HOME и изменение UUID при сохранённом имени.

Синтетическая Btrfs boundary проверяет реальные аргументы parent и delta.
PTY regression sudo сохраняется. CI запускает полный unittest suite.
Runbook обновляется под новый default CLI, автоматическую локальную очистку,
границы Timeshift coverage, отсутствие remote retention и ограничение baseline
для restore-test старых snapshots. Без конфигурации plan/status работают,
передача и очистка не выполняются.
