# WSCONFIG V2 — АРХИТЕКТУРА

Целевое устройство wsconfig. Путь к нему от текущего кода — helpws
plan-v2; как всё устроено сейчас — helpws layers и helpws workstation.

Состояние: принята 2026-10-14 как основа плана, не реализована. Источники:

- документ-направление «wsconfig v2 — целевая архитектура и план миграции»
  (14.10.2026, вне репозитория);
- решения пользователя от 2026-10-14 (раздел 2.4);
- разбор кода на `d40a320`.

# 1. Суть

Инфраструктура и конфигурация живут в разных репозиториях:

- **wsconfig** — ядро: общий код всех машин. Он неизменяем и работает из
  `/nix/store`.
- **Репозиторий конфигурации** — то, чем машины отличаются: хосты,
  каталоги, выбор хостов, личные настройки. Это Git-репозиторий с любым
  именем, один на все машины пользователя. Через свой `flake.nix` он
  закрепляет версию ядра.

Пользователь правит конфигурацию и запускает `ws apply`. Команды модулей
(`ws flatpak install APP`) правят конфигурацию и применяют её сами.
Публикует изменения в Git только явный `ws sync`.

Ubuntu, Nix, home-manager, apt, Flatpak, Podman и Distrobox остаются.
wsconfig не дублирует то, что они уже делают.

# 2. Цели и границы

## 2.1. Цели

1. Обновление инструментов отделено от изменения настроек машин.
2. Конфигурации всех машин — в одном репозитории.
3. Работающий код не зависит от редактируемого checkout.
4. Конфигурация по возможности человекочитаема (TOML).
5. Один сценарий: правка → `ws apply`; команда модуля применяет сама.
6. Сохраняется всё, что работает сейчас: Ubuntu, GNOME, T2, клавиатура,
   Flatpak, Distrobox, Wine, VM, backup и recovery.
7. Общие механизмы написаны один раз. Модули их переиспользуют.
8. Ручная диагностика и вмешательство остаются возможными.

## 2.2. Инварианты

- В PATH из wsconfig только `ws`.
- Применение одно — `ws apply`.
- Команда, изменившая конфигурацию, сама её применяет.
- Ядро неизменяемо. Смена версии — смена pin, старый store path не
  меняется.
- state — только локальное служебное состояние, не источник желаемой
  конфигурации.
- Каталог и выбор yes/no/ask — один механизм для всех модулей с каталогом.
- Скрытых `git commit` и `git push` нет. Коммит и push делает только
  `ws sync`.
- `ws setup` умеет и подключить существующий репозиторий конфигурации, и
  создать новый.
- `ws apply` не обновляет пакеты, не пересоздаёт контейнеры, не удаляет
  данные и не перезагружает машину.

## 2.3. Не цели

- Менеджер ресурсов или транзакций, DAG-планировщик, откат каждого побочного
  эффекта.
- Динамические плагины и сервисный API.
- Замена Nix, home-manager, apt, Flatpak, Podman или Git.
- Декларативность изменяемых данных: Wine prefixes, HOME контейнеров,
  rootfs, образы VM.
- Уход с Ubuntu на NixOS или image-based систему.
- TOML там, где у программы есть свой удобный формат: fish, Ghostty,
  xremap.

## 2.4. Решения

Пользователь, 2026-10-14:

1. Репозиторий конфигурации может называться как угодно. Его checkout по
   умолчанию — `~/wsconfig`, state — `~/.local/state/wsconfig` (раздел 3).
2. Скрытых commit и push нет, публикует `ws sync` (раздел 7).
3. Выбор хоста хранится в файлах хоста, а не пометками в строках каталога
   (9.3).
4. Есть режим разработки ядра: `ws apply --core PATH` (12.3).
5. Порядок миграции: сначала чистка и общие механизмы, разделение
   репозиториев — последним (helpws plan-v2).

# 3. Корни

```text
/nix/store/…-wsconfig     ядро: ws, внутренние исполнители, Nix-модули,
                          общие механизмы, адаптеры железа
~/wsconfig                Git, любое имя репозитория: хосты, каталоги,
                          выбор хостов, личные настройки; flake.nix с
                          входом wsconfig
~/.local/state/wsconfig   только эта машина: хост, путь к ~/wsconfig,
                          шаги setup, история system apply
```

| Корень | Переменная | Кто пишет |
|---|---|---|
| ядро | `WS_CORE` | Nix; руками никто |
| конфигурация | `WS_CONFIG` | пользователь и команды `ws` |
| состояние | `WS_STATE` | `ws` |

Как определяются корни:

- `WS_CORE` — store path пакета `ws`, который запущен; в режиме
  разработки — checkout ядра (12.3).
- `WS_CONFIG` — путь из `WS_STATE/host.json`, который записывает
  `ws setup`. По умолчанию `~/wsconfig`, при setup выбирается другой.
- `WS_STATE` — `$XDG_STATE_HOME/wsconfig`, иначе
  `~/.local/state/wsconfig`.

`ws` передаёт корни внутренним исполнителям через окружение. Исполнители
не ищут репозиторий по `$0` и не угадывают пути.

Состав state:

```text
host.json        id хоста, путь к конфигурации
setup/           шаги setup, возобновление после перезагрузки
system/          applied (ссылка и GC root на установленное дерево), history
keyboard/        резервная копия сочетаний GNOME, флаг отключения xremap
backup/          служебное состояние backup (политика — в конфигурации)
```

Подкаталог появляется, только когда он нужен модулю. Поколения Nix и
home-manager, история Git в state не дублируются.

Вне трёх корней:

- **Сгенерированное home-manager** — манифесты для исполнителей в
  `~/.local/share/workstation/<модуль>`, ссылки в store. Это не источник:
  его пересобирает `ws apply`.
- **Данные технологий** остаются на своих местах: `/etc`, Flatpak user
  installation, хранилище Podman, `~/distrobox/NAME`, Wine prefixes,
  SSH-ключи, образы VM, кеши.

Ссылки из `$HOME`:

- в store — можно;
- в редактируемый код ядра — нельзя;
- на личные настройки в конфигурации (fish, Ghostty) — решается на этапе
  разделения (раздел 16).

# 4. Что где лежит

Правило: что нужно модулю, чтобы работать, — ядро. Что пользователь
выбирает или настраивает — конфигурация.

| Данные | Где |
|---|---|
| `ws`, исполнители, общие механизмы (bash, Python, Nix) | ядро |
| Nix-модули, генераторы манифестов, системное дерево | ядро |
| Адаптеры железа и загрузки (t2-mbp16, legion-go, generic-pc, container-nvidia) | ядро |
| Собственные расширения GNOME, hooks Distrobox, пакеты Nix (xremap, remmina) | ядро |
| apt-пакеты, без которых модуль не работает (virt, steam, gaming, podman/distrobox) | ядро, у модуля |
| Пресеты: клавиатура в стиле macOS, тема GNOME по умолчанию | ядро |
| Хосты: факты, железо, загрузка, включённые слои | конфигурация, `hosts/<id>/host.toml` |
| Выбор хоста yes/no по каталогам | конфигурация, `hosts/<id>/<модуль>.toml` |
| Каталоги: приложения Flatpak с remotes и overrides, определения контейнеров, скрипты | конфигурация |
| Личные apt-пакеты, источники apt хоста | конфигурация |
| Значения GNOME, клавиатуры, терминала; fish, Ghostty, xremap.yml | конфигурация |
| Политика backup | конфигурация |
| Хост этой машины, путь к конфигурации, шаги setup, история apply | state |
| Ключи SSH, токены, учётные данные Git | штатные защищённые места, не Git |

# 5. Репозитории

## 5.1. wsconfig (ядро)

```text
wsconfig/
├── flake.nix           lib.mkConfig, packages.ws, checks
├── bin/ws              единственная публичная команда
├── libexec/            внутренние исполнители модулей
├── lib/                общие механизмы: *.bash, *.py, *.nix
├── <модуль>/           flatpak/, distrobox/, gnome/, keyboard/, windows/, …:
│                       module.nix, исполнители, пресеты, требования apt
├── system/             сборка системного дерева, адаптеры boot/ и hardware/
├── bootstrap/          вход до Nix: ставит Nix и запускает ws setup
├── tests/
└── docs/
```

Модули остаются каталогами верхнего уровня, как сейчас. Переносить их ради
симметрии и создавать пустые каталоги не нужно.

## 5.2. Репозиторий конфигурации

```text
<любое имя>/            checkout: ~/wsconfig
├── flake.nix           вход wsconfig, вызов wsconfig.lib.mkConfig
├── flake.lock          закреплённые wsconfig, nixpkgs, home-manager, …
├── wsconfig.toml       schema — версия схемы этого репозитория
├── hosts/<id>/
│   ├── host.toml       факты хоста
│   ├── flatpak.toml    выбор: yes = […], no = […]
│   ├── boxes.toml
│   ├── widgets.toml
│   ├── scripts.toml
│   └── apt.toml        личные пакеты и источники хоста
├── flatpak/catalog.toml
├── distrobox/catalog.toml
├── scripts/catalog.toml, scripts/files/…
├── gnome/config.toml
├── keyboard/config.toml, keyboard/xremap.yml
├── terminal/fish/…, terminal/ghostty/…
└── backup/config.toml
```

Какой файл появится, решает модуль, когда переходит на конфигурацию. Файлы
без настроек не создаются.

# 6. Публичный интерфейс

| Команда | Смысл | Меняет систему |
|---|---|---|
| `ws setup` | первая настройка машины: подключить или создать конфигурацию, хост, первый apply | да |
| `ws apply [STEP…]` | применить конфигурацию этого хоста (раздел 8) | да |
| `ws check [модуль]` | проверки, только чтение | нет |
| `ws status`, `ws host` | хост, версии ядра и конфигурации | нет |
| `ws update [scope]` | явное обновление: apt, core, inputs, flatpak, box, extensions | да |
| `ws sync` | опубликовать изменения конфигурации (раздел 7) | только Git |
| `ws flatpak`, `ws box`, `ws windows`, `ws widgets`, `ws script`, `ws gnome`, `ws keyboard`, `ws game`, `ws suspend` | команды модулей | по команде |
| `ws system diff`, `check`, `manifest`, `tree` | диагностика системного слоя | нет |
| `ws backup …` | резервирование и восстановление | да |
| `ws container build`, `run`, `status` | хост-контейнер на сервере | на сервере |
| `ws help [тема]` | документация | нет |

Правила:

- Команда модуля, изменившая желаемое состояние, делает три вещи: правит
  конфигурацию, применяет через `ws apply` (можно только нужные шаги),
  сообщает итог.
- `list`, `status`, `enter`, `run`, `check` конфигурацию не меняют и apply
  не вызывают.
- Внутренние исполнители лежат в `libexec` пакета и не попадают в PATH.
- Исключение из правила одного имени — автономный `ws-restore` для Live
  USB. Его собирает `ws backup recovery-export`, на машине он не
  устанавливается.

# 7. Git

- Коммит и push делает только `ws sync`:
  1. коммитит изменения конфигурации с сообщением, собранным из изменений
     (+NAME, -NAME, выбор хостов);
  2. `git pull --rebase` — к этому моменту всё закоммичено, autostash не
     нужен;
  3. `git push`.
- `ws sync` отказывается, если идёт операция Git (rebase, merge,
  cherry-pick, revert, bisect), HEAD отсоединён или у ветки нет upstream.
- Конфликт при rebase — остановка: ws sync печатает, что сделать руками.
  Ничего не форсируется, конфликт не разрешается автоматически,
  восстановления состояния Git нет.
- Пока код и данные в одном репозитории, ограничения строже: ws sync не
  трогает изменения кода и неопубликованные коммиты кода (helpws plan-v2,
  2.7).
- Flake видит только файлы, известные Git:
  - команда, которая создала файл (`ws setup`, `ws script add`, первый
    выбор хоста), делает `git add` ровно этого файла;
  - `ws apply` находит неотслеживаемые файлы конфигурации и называет их;
  - `git add .` не делается никогда.
- `ws apply` и `ws update` в конце сообщают о неопубликованных изменениях.
- Создание удалённого репозитория (GitHub) — только по явному запросу при
  `ws setup`.

# 8. ws apply

Порядок шагов фиксирован в одном месте, в `ws`:

1. Хост и корни. Проверка схемы конфигурации против ядра и неотслеживаемых
   файлов.
2. Новые позиции каталогов (ask) предлагаются одним чеклистом. Без
   терминала они остаются ask, это сообщается.
3. Сборка поколения home-manager и системного дерева.
4. apt: недостающие пакеты, `purge:`, источники, архитектуры. Без
   upgrade.
5. Системное дерево — если отличается от живой системы.
6. home-manager switch.
7. Шаги модулей вне Nix: расширения GNOME, tiling, клавиатура, Flatpak,
   Distrobox, виджеты.
8. Итог по шагам (OK, FAIL, PREFLIGHT) и что осталось сделать: relogin,
   reboot, ручные действия, неопубликованные изменения.

Гарантии:

- Повторный запуск без изменений ничего не ставит и не просит sudo.
- sudo запрашивается только для шагов 4 и 5 и только когда есть что
  делать.
- Ошибка шага — ненулевой код и понятный текст. Остальные шаги идут, если
  от упавшего не зависят.
- Требуется relogin или reboot — это «осталось сделать», а не успех.

`ws apply STEP…` запускает только названные шаги; `home` и `system` —
тоже шаги. `ws switch` и `ws system apply` как отдельные команды не нужны.

# 9. Общие механизмы

Каждый механизм реализован в одном месте. Модули его вызывают и не пишут
свой вариант.

## 9.1. Корни и окружение

`lib/common.bash`, `lib/ws_common.py`: корни (раздел 3), `die`, `need`,
`nix_bin`, запуск внутренних исполнителей. Подключение — одна строка в
начале исполнителя.

## 9.2. Хост и факты

`lib/ws_facts.py`. Через него работают `ws host`, `ws fact [--host HOST]
NAME` и все Python-исполнители.

- Хост — `WS_HOST`, иначе `host.json` в state, иначе поиск по
  `hostname` в `hosts/*/host.toml`.
- Факты читаются через `tomllib`, это работает до установки Nix.
- Значения проверяет только Nix (`assert` в `mkConfig`). Читатель их не
  интерпретирует, поэтому двух семантик нет.

## 9.3. Каталог и выбор хоста

`lib/ws_catalog.py` и `lib/catalog.nix`. Модули с каталогом: Flatpak,
Distrobox, виджеты, скрипты.

- Каталог — всё, что можно поставить. У позиции есть `default`: `ask` (так
  по умолчанию), `no` (не предлагать) или `yes` (ставить без вопроса).
- Выбор хоста — `hosts/<id>/<модуль>.toml` со списками `yes` и `no`.
  Позиция, которой нет ни в одном из списков, получает `default`
  каталога. Каждая машина пишет только свои файлы. Порядок `yes` значим
  там, где модулю нужен порядок (виджеты: кнопки панели).
- Операции:
  - `state`, `set`, `remove` (снять с хоста; запись каталога остаётся
    для других хостов);
  - `delete` (удалить из каталога, явная команда);
  - `offer`: чеклист lib/ws_select.py, отмена оставляет ask, без
    терминала — сообщение;
  - `summary` для `ws sync`.
- Новая позиция, установленная на хосте A, попадает в каталог и в `yes`
  хоста A. Хост B видит её после синхронизации Git как ask и без решения
  пользователя не ставит.
- Модуль может хранить в файле хоста и свои значения для позиций каталога.
  Пример — overrides Flatpak только этого хоста (раздел 10).
- Запись — через tomlkit и в каталоге, и в файлах хоста. Комментарии и
  порядок сохраняются. Только читающие места (bootstrap, `ws fact`)
  обходятся `tomllib`.
- Nix читает выбор только для сборки, например ссылок .desktop на то, что
  стоит.

## 9.4. Контракт проверок

`lib/check.bash` и `lib/ws_check.py` дают один формат. `ws check`
запускает проверки модулей с `--json` и читает только объект:

```json
{"status": "pass|warn|fail", "passes": 0, "warnings": 0, "failures": 0,
 "messages": [{"level": "pass|warn|fail|info", "text": "…"}]}
```

Без `--json` печатаются те же сообщения для человека. Проверка только
читает систему.

## 9.5. Шаги

Общий только код обхода шагов: проверка имён, фильтр по аргументам,
заголовок шага, сбор и печать итога. Смысл результата каждая команда
определяет сама, универсального обработчика с режимами нет:

- apply: 0 — OK, 69 — PREFLIGHT (нужен relogin), остальное — FAIL;
- check: объект контракта 9.4, итог по WARN и FAIL;
- update: 0 — OK, остальное — FAIL.

## 9.6. Манифесты Nix → исполнители

Nix собирает для исполнителя JSON (`builtins.toJSON`) в
`~/.local/share/workstation/<модуль>/`. Исполнители читают его одним
читателем из ws_common.py. Свой формат остаётся только там, где файл
читает чужая программа: `containers.ini` для `distrobox assemble`,
.desktop, keyfile overrides Flatpak, `dconf`.

## 9.7. apt

Один резолвер собирает список пакетов хоста:

- требования модулей ядра — только включённых слоёв хоста;
- общий список конфигурации;
- `hosts/<id>/apt.toml`.

`apt_install` применяет его: ставит недостающее, делает `purge:`,
добавляет источники и архитектуры. Обновлением занимается только
`ws update apt`. Тот же список читают `ws check apt` и baseline.

## 9.8. Системное дерево

Семантика нынешнего `ws system` сохраняется:

- Nix строит дерево и manifest (`file`, `esp`, `unit`, `restart`,
  `watch`);
- шаг `system` сохраняет копии и ставит только отличающиеся файлы, затем
  выполняет зависимые действия (initramfs, update-grub, sysctl, GDM);
- ESP не трогается, перезагрузки нет.

## 9.9. Git-операции

`lib/ws_git.py`: `sync`, `git add` созданных файлов, поиск
неотслеживаемых. Других мест, где ws вызывает `git commit`, `git push` или
`git add`, нет.

# 10. Форматы данных

`hosts/<id>/host.toml`:

```toml
[host]
hostname = "MacBookPro-k"
user = "king"

[platform]
hardware = "t2-mbp16"
boot = "refind-grub-recovery"
kernelParams = ["…"]
displayScale = "1.5"

[layers]
vm = true
nativeSteam = false
gameMode = false
widgets = true
```

`hosts/<id>/flatpak.toml`:

```toml
# Flatpak на mbp16 (ws flatpak …): yes — стоит, no — отказ;
# остальное — default каталога.
yes = ["org.gimp.GIMP", "com.mikrotik.WinBox"]
no = ["com.valvesoftware.Steam"]

# Overrides только этого хоста, поверх общих из каталога: свои значения
# и skip — общие, которые здесь не применяются.
[overrides."com.anydesk.Anydesk"]
env = { GDK_SCALE = "1" }
skip = ["talk org.kde.StatusNotifierWatcher"]
```

`flatpak/catalog.toml`:

```toml
[remotes]
flathub = "https://dl.flathub.org/repo/flathub.flatpakrepo"

[apps."org.gimp.GIMP"]
remote = "flathub"

[apps."com.anthropic.ClaudeDesktop"]
remote = "flatpark"
filesystems = ["host"]
talk = ["org.freedesktop.Flatpak"]
```

Правила:

- Булевы значения — true/false. `ws fact` печатает их как yes/no для
  проверок в shell.
- Значения задаются понятными параметрами, а не строками GVariant. Языка
  условий в TOML нет: условия — в Nix.
- Порядок слияния: значения ядра по умолчанию → общая конфигурация →
  хост. Скаляр берётся последний, список хоста заменяет общий. Если
  значение не сливается однозначно — ошибка с именем параметра.
- Overrides Flatpak на хосте: одно значение на ключ (имя env, путь
  filesystem, имя шины). Значение хоста заменяет общее с тем же ключом,
  `skip` убирает общее.
- Один ключ dconf — один владелец (GNOME, клавиатура, Tiling Assistant).
  Пересечение — ошибка сборки.
- `wsconfig.toml`: `schema` — одна версия на весь репозиторий
  конфигурации. Ядро знает, какие версии читает. Несовпадение — ошибка до
  сборки: «нужна миграция». Файлы пользователя молча не переписываются.

# 11. Контракт модуля

| Часть | Нужна | Что делает |
|---|---|---|
| `module.nix` | обычно | читает разрешённую конфигурацию, строит файлы home-manager, системного дерева и манифесты |
| TOML в конфигурации | если есть настройки | данные пользователя |
| Нативные файлы | по потребности | fish, YAML, .desktop, hooks |
| `apply` | если есть работа вне Nix | Flatpak, Podman, расширения GNOME |
| `check` | желательно | только чтение, контракт 9.4 |
| Команды `ws <модуль> …` | по потребности | свои операции; меняющие — через 9.3 и apply |
| Требования apt | если есть | пакеты, без которых модуль не работает (9.7) |

Модуль регистрируется строкой в таблице `ws`: имя, исполнитель, шаги
apply и check. Динамической загрузки нет.

Модуль получает корни, id хоста и свой манифест. Других путей он не
знает.

# 12. Пакет, пути, разработка

## 12.1. Пакет ws

- `packages.ws` содержит `$out/bin/ws` и `$out/libexec/wsconfig/*`, плюс
  общие механизмы, расширения GNOME, hooks и docs для `ws help`.
- home-manager ставит `ws` в PATH.
- CLI и Nix-модули всегда из одной ревизии wsconfig: один pin в
  `flake.lock` конфигурации.

## 12.2. Вызовы извне

- Из Nix (сочетания GNOME, юниты systemd, .desktop) — пути в store
  напрямую.
- Где путь нужен заранее (JS расширений) — стабильная ссылка
  `~/.local/share/workstation/libexec` на текущий пакет. Её ставит
  home-manager.
- Distrobox: hook — `sh /run/host/nix/store/…`. Distrobox монтирует
  корневые каталоги хоста в `/run/host`, shebang из store внутри
  контейнера не нужен.

## 12.3. Режим разработки ядра

- `ws apply --core PATH` — сборка с `--override-input wsconfig path:PATH`:
  ядро из локального checkout вместо pin. `flake.lock` не меняется.
- `PATH/bin/ws`, запущенный из checkout ядра, берёт этот checkout как
  `WS_CORE`. Так правку можно проверить без apply.
- `ws update core` переводит pin на новую ревизию по шагам: обновить
  `flake.lock`, собрать, проверить схему, применить. Если шаг не удался,
  `flake.lock` возвращается.

# 13. ws setup

Вход на чистой Ubuntu — bootstrap. Он ставит git и Nix из apt и запускает
`ws setup` из закреплённого wsconfig (`nix run`). Второй постоянной
системы команд bootstrap не создаёт.

`ws setup` предлагает два равноправных сценария.

**A. Подключить существующий репозиторий** — `ws setup --repo URL|PATH`:

1. Проверить, что репозиторий доступен и это Git.
2. URL клонируется в выбранный каталог (по умолчанию `~/wsconfig`), только
   в пустой. Существующий каталог не удаляется, force checkout не
   делается.
3. Проверить схему.
4. Выбрать существующий хост или создать новый.

**B. Создать новый** — `ws setup --new`:

1. Создать каталог без перезаписи и сделать `git init`.
2. Записать минимальный проект: `flake.nix`, `flake.lock` с текущей
   версией wsconfig, `wsconfig.toml`, шаблон хоста, `.gitignore`, README.
3. Хост — по инвентаризации машины. Сомнительное подтверждает человек.
4. Новые файлы попадают в индекс. Коммит и push — только с согласия
   пользователя. Удалённый репозиторий — опционально.

Общее для обоих сценариев:

- в state записываются только хост и путь;
- первичный выбор приложений, контейнеров, виджетов и скриптов — одним
  чеклистом (9.3);
- дальше подготовка системы (Btrfs, группы, ключи) и первый `ws apply`;
- шаги отмечаются в `WS_STATE/setup` и продолжаются после перезагрузки.

Для T2 и rEFInd — отдельный проверенный путь. Разметка диска и загрузка
без явного действия человека не меняются.

Граница: `ws setup` готовит ОС, файловую систему, Nix, группы и ключи;
`ws apply` применяет уже описанную машину. `ws apply` не размечает диски и
не переустанавливает ОС.

# 14. Изменяемые данные и секреты

- Wine prefixes, HOME контейнеров (`~/distrobox/NAME`), rootfs, образы VM
  и данные Flatpak-приложений не декларативны.
  - `ws apply` их не удаляет и не пересоздаёт.
  - Пересоздание — только явная команда (`ws box recreate NAME`). Если
    образ или пакеты изменились, apply предупреждает и называет команду.
- Секретов в репозитории конфигурации нет: ключи SSH, токены и учётные
  данные остаются в штатных местах. Диагностические архивы (`ws collect`)
  проверяются на них.

# 15. Хост-контейнер

Хост с `boot = "container"` (helpws plan-wsgnomebox) описан в
конфигурации, как любой другой. Образ собирается из конфигурации и
закреплённой версии wsconfig: контекст сборки — оба репозитория. Внутри
контейнера работают те же `ws apply` и `ws check`, без шагов, которых у
контейнера нет: загрузчик, udev, xremap.

# 16. Открытые вопросы

Решаются на своём этапе плана (helpws plan-v2):

1. Личные настройки (fish, Ghostty): ссылки в конфигурацию (правка без
   apply) или копии в store (правка → apply).
2. Где после разделения лежит checkout ядра: `~/wsconfig` занимает
   конфигурация.
3. Сгенерированное home-manager: оставить `~/.local/share/workstation` или
   переименовать в `~/.local/share/wsconfig`, как state.
4. Профили (общие наборы настроек для нескольких хостов). Пока слои
   включаются фактами `[layers]`; профили появятся, если хосты начнут
   повторять одинаковые наборы.
5. Создание удалённого репозитория при `ws setup --new`.
