# WSCONFIG V2 — ЧИСТКА, ОБЩИЕ МЕХАНИЗМЫ, ДВА РЕПОЗИТОРИЯ

Путь от текущего кода (`d40a320`) к архитектуре ws help architecture-v2.
Цель — неизменяемое ядро wsconfig из `/nix/store` и отдельный репозиторий
конфигурации. Это Git-репозиторий с любым именем, один на все машины:
хосты, каталоги, выбор хостов, личные настройки. Публичная команда одна —
`ws`, применение одно — `ws apply`. По пути убирается legacy. Механизмы,
которые сейчас написаны по нескольку раз, выносятся в общие и
переиспользуются.

Направление задал документ «wsconfig v2 — целевая архитектура и план
миграции» от 14.10.2026. Он лежит вне репозитория и задаёт направление, а
не готовое решение. Принятое — в ws help architecture-v2.

Состояние: этапы 0–7 выполнены 2026-10-14, этап 8 (два репозитория, с
шагом 7.5) — 2026-10-15: ядро `~/Projects/wsconfig` (kkkingqz/wsconfig),
конфигурация `~/wsconfig` (закрытый kkkingqz/wsbodya). Дальше — этап 9
(ws setup), детальный план — раздел 13.

# 1. Решения

Приняты пользователем 2026-10-14:

1. Порядок: сначала чистка и общие механизмы в текущем репозитории.
   Разделение на ядро и репозиторий конфигурации — последним (этап 8).
2. Коммиты: скрытых commit и push нет. Изменения конфигурации публикует
   явная команда `ws sync` (2.7).
3. Выбор хоста (yes/no/ask) хранится в файлах хоста, а не пометками в
   строках общего каталога (этап 3).
4. Режим разработки ядра: `ws apply --core PATH` собирает с локальным
   checkout ядра вместо закреплённой версии (этапы 5 и 8).
5. Репозиторий конфигурации может называться как угодно. Его checkout по
   умолчанию — `~/wsconfig`, state — `~/.local/state/wsconfig`.

# 2. Цель

```text
/nix/store/…-wsconfig     ядро: ws, внутренние исполнители, Nix-модули,
                          общие механизмы, адаптеры железа
~/wsconfig                Git, любое имя репозитория: хосты, каталоги,
                          выбор хостов, личные настройки; flake.nix с
                          входом wsconfig
~/.local/state/wsconfig   только эта машина: хост, путь к ~/wsconfig,
                          шаги setup, история system apply
```

Было до этапа 8: по пути `~/wsconfig` лежал checkout ядра с данными, а
state — в `~/.local/state/workstation`. Подробнее — ws help architecture-v2:
инварианты, общие механизмы, форматы, `ws apply`, `ws sync`, `ws setup`.

# 3. Правила этапов

- Шаг — отдельный коммит с тестами, push сразу.
- В одном шаге не меняются одновременно формат данных, место хранения и
  способ запуска.
- Этапы 1–4 и 7 не меняют поведения, кроме `ws sync` (2.7). Проверка —
  чистое сравнение выходов (0.1): нет неразрешённых различий содержимого
  системных файлов и манифестов. Различия одних путей `/nix/store`
  допускаются.
- Живой хост сейчас один — mbp16. legiongo и wsgnomebox есть только в
  репозитории. wsvm — тестовая VM миграции на Nix (ws help history-nix);
  жива ли она — выясняется в 0.3.
- На mbp16 этап применяется только с подтверждения пользователя. Перед
  этим — `ws checkpoint create`, после — `ws check`.
- Детальный план этапов 7–10 пишется перед их началом, по коду того момента.

# 4. Этап 0. База

0.1. Сравнение выходов: `tests/compare-outputs BASE [--allow FILE]`, не
публичная команда. Нужно этапам 1–8.

Скрипт строит `system-HOST` и home-manager `activationPackage` всех хостов
на коммите BASE (через git worktree) и на рабочем дереве. Различия он
раскладывает по видам:

1. содержимое управляемых системных файлов — записи `file` и `esp`
   manifest с одним путём назначения;
2. манифесты и параметры: строки manifest (юниты, restart, watch), список
   и содержимое файлов home-manager, манифесты для исполнителей, dconf;
3. только пути `/nix/store`: файлы совпадают после замены
   `/nix/store/<hash>-` на один шаблон;
4. разрешённые шагом: пути и шаблоны из `--allow FILE`.

Печатаются все виды. Ненулевой код дают только виды 1 и 2 вне
разрешённых — это «чистое сравнение» в критериях этапов. Вид 3 только
показывается: при смене реализации Nix пути и ссылки в store меняются,
хотя конфигурация та же. Сильнее всего это проявится при переходе на два
flake.

Файл, отличающийся одними путями store, скрипт прослеживает в пути, на
которые он ссылается (пары по имени): изменённый скрипт, на который
указывает юнит, попадает в вид 1 или 2 как сам юнит, с цепочкой после
`<-`. Цели ссылок в checkout (`~/wsconfig/bin/…`) сравниваются как
строки: это сам код, его проверяют тесты.

Анализатора зависимостей нет. Что различие ожидаемо, подтверждает
разработчик: вносит его в allow-файл шага, а содержимое файла приводит в
сообщении коммита.

0.2. Инвентарь вызовов: кто вызывает каждый файл `bin/` — .desktop, юниты
systemd, сочетания GNOME, JS расширений, fish, hooks Distrobox, тесты,
docs. Результат — приложение A. Нужен шагам 1.1, 2.8 и этапу 5.

0.3. Снимок mbp16, с подтверждения пользователя: `ws checkpoint create
v2-base`, `ws check` без FAIL. Отдельно — нет ли на mbp16 (и на wsvm,
если она жива) файлов, которые убирает шаг 1.2, и каталогов из шага 1.3.

Проверено 2026-10-14, только чтение: на mbp16 нет ни одного файла шага 1.2
(`70-workstation-uinput.rules`, `/etc/tiny-dfr/config.toml`,
`tiny-dfr-sleep.service`, `70-ws-dgpu-t2gmux`, `system-backup-snapshot`,
`41_backup_snapshot`, `/boot/recovery*`, `/.snapshots`), ни одного

# 6. Этап 2. Общие механизмы

Каждый пункт — один общий файл. Все места, где механизм написан заново,
переходят на него. Поведение не меняется, кроме 2.7.

2.1. Корни и общие функции: `lib/common.bash`, `lib/ws_common.py`.

- Корни: `WS_CORE` — код (bin/, lib/, gnome/extensions, hooks), `WS_CONFIG`
  — данные (nix/hosts, каталоги, выбор хостов), `WS_STATE` — state (пока
  `~/.local/state/workstation`, с 2.9 — `~/.local/state/wsconfig`). Пока
  оба первых указывают на checkout,
  переменная тестов `WSCONFIG` задаёт оба. Этапы 5 и 8 меняют только их
  значения.
- `die`, `need`, `nix_bin`. `ws` экспортирует корни, когда вызывает
  внутренние исполнители.
- Переходят: 34 файла с `repo=…readlink -f "$0"`, 18 копий `die`, 3 копии
  `nix_bin` (ws, ws-checkpoint, wswidgets), `REPO`/`CFG` wsflatpak,
  `bin_dir` wsbox и wswidgets.
- Готово: `readlink -f "$0"` остаётся только в строке подключения common.

2.2. Хост и факты: один читатель, `lib/ws_facts.py`.

- Строковые факты facts.nix (то же выражение, что `fact_in`), поиск хоста
  по hostname, `WS_HOST`, проверка имени хоста для выбора. Сейчас имя
  проверяют wsbox, wswidgets и `ws_marks.check_host`.
- `ws host` и `ws fact` вызывают его. Новое: `ws fact --host HOST NAME`.
- Переходят: `fact_in` в bin/ws и setup.sh, `fact()` в setup_marks.py, sed
  `user` и grep `boot` в ws-container, `host_fact` в lib/check.bash.
- Нестроковый `container` ws-container до этапа 4 читает `nix eval`.

2.3. apt-списки хоста. `apt_lists` в lib/apt.bash — единственное место, где
по фактам выбираются списки: nix/hosts/apt.txt, список хоста,
machine-apt.txt, virt, steam, gaming. `apt_lines` — единственная очистка
строк. Переходят `ws check apt` (bin/ws) и ws-baseline. bootstrap.sh и

2.4. Контракт проверок: `lib/ws_check.py` — то же, что lib/check.bash
(pass, warn, fail, info, `--json`, итог).

- Переходят: wsflatpak (свои `report`/`finish` в `cmd_check`) и wsgame
  (свой класс).
- Разбор результатов в `ws check` (сейчас встроенный Python в bin/ws) —
  функция того же модуля.
- Тест: одни и те же сообщения дают одинаковый JSON у bash- и
  Python-версии.

2.5. Обход шагов. Общим становится только код, который сейчас повторяется
в `cmd_apply`, `cmd_update` и `cmd_check`: проверка имён шагов, фильтр по
аргументам, заголовок шага, сбор строк итога и печать итога. Это
небольшие функции в bin/ws.

Смысл результата каждая команда определяет сама:

- apply различает OK, PREFLIGHT (код 69) и FAIL;
- check читает объект контракта 2.4 и считает WARN и FAIL;
- update — OK или FAIL.

Универсального обработчика с режимами нет. Вывод не меняется
(test_ws_update).

2.6. Манифесты для инструментов — JSON.

Nix пишет `builtins.toJSON`, инструменты читают одним читателем из
ws_common.py. bash-инструменты вызывают `ws_common.py get FILE KEY…`: jq в
apt-списках нет. По одному манифесту за коммит:

- distrobox: exports.ini, boxes.ini (wsbox и wswin, у каждого свой
  `ini_value`);
- windows/apps.ini (wswin);
- flatpak: remotes.conf, apps.conf, overrides/APP.conf (wsflatpak);
- keyboard: gnome-shortcuts.tsv, tiling-bindings.tsv;
- gnome: settings.conf, extensions;
- t2bce/sources, t2gmux/source.

Свои форматы остаются там, где файл читает чужая программа: containers.ini
(`distrobox assemble`), .desktop, xremap.yml.

Готово: `ini_value` нет, своих разборов INI и TSV в инструментах нет.
В сравнении выходов отличаются только манифесты, разрешённые шагом.

2.7. `ws sync` (решение 2). Меняет поведение.

До разделения код и данные лежат в одном репозитории. Поэтому
`ws sync [--dry-run]` здесь осторожнее, чем в конечной архитектуре.

Он отказывается и объясняет почему, если:

- идёт операция Git: rebase, merge, cherry-pick, revert, bisect;
- HEAD отсоединён;
- есть изменения вне файлов данных, в индексе или в рабочем дереве. Код
  коммитит разработчик сам;
- есть неопубликованные локальные коммиты, которые меняют не только файлы
  данных: push опубликовал бы их молча.

В обычном случае:

1. показывает изменённые файлы данных и коммитит их; сообщение
   собирается из изменений (+NAME, -NAME, выбор хостов — как сейчас
   `ws_marks.py summary`);
2. дальше по состоянию Git, как в ws help architecture-v2, раздел 7:
   - нет remote — только локальный коммит;
   - есть remote и upstream — `git pull --rebase` (рабочее дерево уже
     чистое, autostash не нужен), затем `git push`;
   - есть remote, нет upstream — локальный коммит и сообщение, как
     настроить upstream.

Конфликт при rebase — остановка. ws sync печатает, что сделать руками:
`git status`, разрешить конфликт и `git rebase --continue` или
`git rebase --abort`. Автоматического восстановления состояния Git нет.

После разделения (этап 8) в репозитории конфигурации всё — данные.
Ограничение на изменения вне файлов данных уходит, остальные проверки
остаются.
- Файлы данных сейчас — flatpak/apps.txt, flatpak/overrides.txt,
  distrobox/hosts.txt, widgets/widgets.txt и flake.lock, после этапа 3 —
  каталоги и файлы выбора. Список хранится в одном месте bin/ws, его же
  читают switch и `ws check repo`.
- Автокоммиты убираются:
  - `commit_tool_lists` в `ws switch`;
  - коммит flake.lock в `wswidgets update`.
- `ws update nix` и `ws apply` в конце пишут «не опубликовано: …; ws sync».
  `git add` файлов данных перед сборкой остаётся: без него flake их не
  видит.
- setup.sh: новый хост и выбор публикуются после вопроса «Опубликовать
  (ws sync)? [Y/n]». Сейчас их коммитят и пушат без вопроса `new_host` и
  `step_choices`.
- `ws check repo`: INFO о неопубликованных файлах данных.

2.8. Модули — через `ws`.

- Таблица модулей в bin/ws: `ws flatpak|box|windows|widgets|game|keyboard|
  gnome|suspend|backup …` вызывает нынешний исполнитель. Fish-дополнение
  `ws` берёт модули из таблицы, как сейчас из `ws steps`.
- Старые имена (wsflatpak, wsbox, wswin, wswidgets, wsgame, ws-keyboard,
  ws-gnome, wsbackup, ws-suspend) пока остаются: их вызывают .desktop
  (`Exec=wswin run`), сочетания и docs (приложение A). Убираются на этапе 5.
  docs и подсказки в выводе переходят на `ws <модуль>`.
- `ws-restore` остаётся отдельным: он работает с Live USB без wsconfig
  (ws help recovery).
- `ws-keyboard-install-extensions` ставит все расширения GNOME из
  gnome/extensions, не только клавиатурные. Он переходит в модуль gnome
  (`ws gnome extensions`), шаг apply `extensions` вызывает его там.

2.9. state → `~/.local/state/wsconfig` (решение 5). После 2.1 путь задан в
одном месте — `WS_STATE`. Его читают 16 файлов: bin/ws, ws-baseline,
ws-battery, ws-check-backup, ws-check-repo, ws-checkpoint, ws-collect,
ws-keyboard*, keyboard/keyboard.nix, keyboard/xremap.nix, lib/backup.py,
setup.sh и дополнения fish.

Перенос на живых хостах — при применении шага, на mbp16 — с
подтверждения пользователя:

1. Старый каталог копируется (`cp -a`), а не переносится. Он остаётся
   нетронутым и удаляется только руками, когда новый проверен.
2. GC root создаются заново в новом месте. Копия ссылки не
   регистрируется как корень, и после удаления старого каталога Nix собрал
   бы деревья. Это касается `system/applied` (ws system apply) и
   `home`/`system` каждого checkpoint (ws-checkpoint): `nix build
   --out-link НОВЫЙ ЦЕЛЬ` для каждой ссылки.
3. Проверка нового каталога:
   - резервная копия сочетаний GNOME (keyboard/) на месте;
   - `ws checkpoint list` показывает те же checkpoint;
   - история `ws system apply` и служебное состояние backup и recovery
     читаются;
   - `ws check` без новых FAIL.

Кода переноса в ws нет: он остался бы legacy. Snapshot Timeshift до шага
восстанавливает старый код вместе со старым путём, они совпадают.

Готово этапа 2: каждый механизм живёт в одном файле, тесты зелёные,
сравнение выходов чистое.

# 7. Этап 3. Каталоги и выбор хоста

Решение 3.

Каталог модуля — всё, что вообще можно поставить:

- Flatpak: `flatpak/catalog.toml` — remotes и приложения. У приложения
  remote и overrides: filesystems, env, talk.
- Distrobox: определения пока в distrobox.nix, в TOML — на этапе 7.
- Виджеты: `lib.catalog` закреплённого wswidgets.

У позиции каталога есть `default` — что получает хост без своего выбора:

- `ask` — предложить (так по умолчанию);
- `no` — не предлагать; сейчас так (`all=no`) у t2bce-build и
  touchbar-build;
- `yes` — включить на всех хостах без своего выбора, без вопроса. Это
  явное решение «для всех». Команды (`ws flatpak install`, `ws box create`)
  создают записи только с `ask`.

Выбор хоста — `nix/hosts/HOST/MODULE.toml`:

```toml
# Flatpak на mbp16 (ws flatpak …): yes — стоит, no — отказ. Чего нет ни
# там, ни там, — ask: ws apply предложит.
yes = ["org.gimp.GIMP", "com.mikrotik.WinBox"]
no = []

# Overrides только этого хоста, поверх общих из каталога.
[overrides."com.anydesk.Anydesk"]
env = { GDK_SCALE = "1" }
skip = ["talk org.kde.StatusNotifierWatcher"]
```

Каждая машина пишет только свои файлы. Конфликта в одной общей строке, как
у нынешних пометок, нет. У виджетов порядок `yes` — порядок кнопок на
панели этого хоста. Сейчас порядок общий: порядок строк widgets.txt.

Overrides Flatpak бывают общие и свои для хоста, как сейчас:

- Общие — в записи приложения в каталоге. Они действуют на каждом хосте,
  где приложение стоит (сейчас `all=yes`).
- Свои — секция `[overrides."APP"]` в flatpak.toml хоста:
  - свои filesystems, env, talk (сейчас `HOST=yes all=no`);
  - `skip` — общие значения, которые на этом хосте не применяются
    (сейчас `HOST=no`).
- На хосте одно значение на ключ (имя env, путь filesystem, имя шины), как
  сейчас. Значение хоста заменяет общее с тем же ключом.
- Команды `ws flatpak filesystem`, `env`, `talk` пишут в каталог, с
  `--host` — в файл хоста.
- `un…` снимает значение: своё — из файла хоста, общее — через `skip`
  хоста; с `--all` общее удаляется из каталога.

Сегодня у всех строк overrides.txt `mbp16=yes all=yes` (2026-10-14). При
конвертации все они уходят в каталог, секций хостов не появится.

# 10. Этап 6. Один ws apply

Порядок шагов (уточняется тестами загрузки, GDM, клавиатуры и контейнера):

1. Хост и корни. Неотслеживаемые файлы flake — ошибка с подсказкой
   `git add`.
2. Новые позиции всех каталогов предлагаются одним чеклистом
   (`ws_catalog offer --all`). Без терминала они остаются ask, об этом
   сообщается.
3. Сборка поколения home-manager и дерева system.
4. apt: недостающие пакеты, purge:, source:, arch: (`apt_install`, без

5. system: только если дерево отличается от живой системы (логика

6. home-manager switch.
7. Шаги модулей (extensions, tiling, keyboard, flatpak, box, widgets) —

   неопубликованные данные (`ws sync`).

  `system`.

  `purge:` сначала через `apt-get -s purge`: если apt удалил бы ещё что-то,
  шаг останавливается и называет пакеты (`apt_purge_check`, и в
  bootstrap.sh).
- system — libexec/ws-system: весь системный слой из bin/ws (`diff`,
  `check`, `manifest`, `tree`, `pending`, `apply`); `ws system` — только
  чтение. `pending` сравнивает без sudo: файлы, юниты,
  /etc/default/keyboard и grub, первый /boot/ws. Причины перезагрузки apply
  пишет в `WS_APPLY_NOTES`, итог `ws apply` их показывает.
- На хосте-контейнере apt — в образе, system применяется (новее образа).
- Команды модулей сами вызывают `ws apply МОДУЛЬ` (`apply_module` в
  common.bash и ws_common.py; внутри ws apply — нет, `WS_APPLYING`):
  `ws flatpak install|manage|unmanage|remove`, overrides,
  `ws widgets enable|disable|update`, `ws box remove` (`ws apply home`:
  ярлыки). `-n` у widgets — `--no-apply`.
- `ws update nix` и `ws widgets update`: flake.lock возвращается только
  при коде 2.
- `ws switch` и `ws system apply` убраны; `ws switch` отвечает подсказкой
  на `ws apply`. bootstrap.sh — `ws apply home` (HOME_MANAGER_BACKUP_EXT),
  setup.sh — `ws apply`.
- Тесты: tests/ws_fixture.py (ядро и конфигурация с заглушками nix, sudo,
  apt, dpkg), test_ws_steps — порядок, частичный запуск, идемпотентность
  (второй запуск без sudo и установок), остановка purge.
- Комментарий в system/files/usr/local/sbin/ws-boot-links ещё называет
  `ws system apply`: правка изменила бы системный файл и потребовала sudo.
  Исправить при ближайшем настоящем изменении (как refind.conf, этап 4).

# 11. Этап 7. Данные модулей в TOML

Детальный план — 2026-10-14, по коду после этапа 6 (`bb2ac93`).

Из Nix-выражений в TOML переходит то, что пользователь правит руками. Логика
остаётся в Nix: условия, пути, вычисления по фактам, перевод в GVariant и
формат манифестов. Пресеты — ядро, выбранные значения — конфигурация
(ws help architecture-v2, разделы 4 и 10).

Правила этапа:

- Один модуль — один шаг: коммит с тестами, push.
- Сравнение выходов (0.1) после шага — без различий содержимого: в TOML
  те же значения, что были в Nix. Поэтому `ws apply` на mbp16 после шага
  ничего не меняет в системе и сессии, только пересобирает.
- Комментарии Nix-файлов переносятся в TOML.
- Где порядок значим (манифест контейнеров, список расширений), TOML —
  массив таблиц `[[…]]`: `builtins.fromTOML` порядок ключей таблицы не
  хранит.
- Файлы до этапа 8 лежат в этом репозитории по путям архитектуры
  (`distrobox/catalog.toml`, `gnome/config.toml`, …). На этапе 8 они
  уходят в репозиторий конфигурации как есть.
- Новые TOML — файлы данных `ws sync` (`data_patterns` в bin/ws): их правит
  пользователь, коммитит и публикует `ws sync`, а не разработчик.

## 7.0. Общий читатель (lib/config.nix)

## 7.1. Distrobox → distrobox/catalog.toml


  Так выходят нынешние 144 и 192 на mbp16. Число в TOML заменяет
  вычисленное.
- Ключи: name, image, packages, pre_init_hooks, init_hooks, gpu, default,
  exports, settings (init, nvidia, pull, root, start_now, entry), windows.
  Схема — lib/schema.nix.
- `ws_catalog.box_catalog` без собранного boxes.json (setup.sh до Nix)

## 8.6. Отдельное ядро: --core, update core, sync, check repo

- `ws apply --core PATH`, также в `ws diff`, `ws update` и
  `ws checkpoint`: общие аргументы nix в lib/common.bash —
  `--override-input wsconfig path:PATH`. flake.lock не меняется. Пока
  входа wsconfig нет (до 8.9), `--core` — ошибка.
- `ws update core`: `nix flake update wsconfig`, сборка, проверка схемы,
  apply. flake.lock возвращается при коде 2, как в `ws update nix`.
  `ws update nix` обновляет nixpkgs и home-manager конфигурации.
- Режим отдельной конфигурации: в корне конфигурации нет `bin/ws`. Режим
  одного репозитория (`data_patterns`) работает до 8.11.
- `ws sync` в отдельной конфигурации: все отслеживаемые изменения и файлы
  в индексе. Новые неотслеживаемые файлы он не добавляет, а называет
  (`git add ФАЙЛ`). Сообщение коммита — как сейчас для каталогов, выбора и
  flake.lock, для прочих файлов — их имена.
- Неотслеживаемые файлы: `ws apply` их не добавляет, а называет, код 2
  (архитектура, раздел 7). Команды, которые создают файл (первый выбор
  хоста в lib/ws_catalog.py), сами делают `git add` этого файла.
- `ws check repo` в конфигурации: схема, неотслеживаемые файлы,
  неопубликованное. Проверки кода (`.gitignore` сгенерированного, ссылки)
  — только в checkout ядра.
- Тесты: `Workspace` с отдельной конфигурацией (8.1) — sync, apply,
  update core, `--core`.

Сделано: `use_core` и `nix_args` в lib/common.bash; `--core` после имени
команды у apply, diff, news, update, checkpoint; аргументы — во всех
сборках (ws, ws-system, ws-checkpoint, home-manager switch). Отличие от
плана: checkout git берётся как `git+file:PATH` (отслеживаемые файлы с

git-каталог — `path:`. `ws update core` (нет входа wsconfig — «nothing to

ядра.

## 8.7. checkpoint, baseline, container

- `ws checkpoint create`:

# 15. Риски

- Загрузка mbp16 (rEFInd, T2). Логика system apply до этапа 6 не меняется.
  Перед применением этапа на mbp16 — checkpoint, после — `ws check`.
- Конвертация выбора (этап 3) может потерять позицию. Защита — тест
  эквивалентности состояний для всех хостов.
- Hooks Distrobox из store (этап 5). Известный случай — install-hook
  ntsync, он берёт пользователя из владельца файла. Проверка на arch до
  перевода остальных.
- Частичный apply со старым манифестом. Защита — общие стадии Nix в
  каждом частичном apply (этап 6).
- Перенос state (2.9) теряет GC root или резервные копии. Защита —
  копирование вместо переноса, корни заново, проверка до удаления
  старого.
- Без автокоммитов выбор не доезжает до другой машины. Защита —
  напоминание в выводе apply и switch, INFO в `ws check repo`.
- docs и дополнения со старыми именами. Защита — test_helpws и проверка по
  приложению A перед удалением имён.
- Перенос checkout ядра ломает контейнеры, созданные до этапа 5: их hooks
  в checkout. Защита — `ws box check` и recreate до переноса (8.12).
- Ссылка из `$HOME`, которую ставят и ядро, и `home/` конфигурации.
  Защита — ошибка сборки с именем файла (8.3).
- Закрытый CONFIG на новой машине недоступен без входа в GitHub. Защита —
  setup.sh клонирует после `gh auth login` (8.10).
